笔记库不同于代码——它记录的是长期积累，一旦误删或损坏，损失不可逆。因此给知识库加上**版本控制与自动备份**，是基础设施而非可选项。

> 本文中的仓库地址、路径均为通用示例；真实密钥与私有仓库信息请勿写入公开笔记。
{: .prompt-info }

## 一、为什么笔记库需要 Git

| 需求 | Git 的解法 |
|---|---|
| 误删防丢 | 每次提交都是一个快照，可回退到任意版本 |
| 改动可追溯 | 每次提交写清"改了什么"，形成时间线 |
| 远程备份 | push 到**私有**仓库，异地多一重保险 |
| 多端同步 | 另一台设备 pull 即同步全部笔记 |
| 大胆试验 | 建分支随意折腾，主分支不受影响 |

> 和写代码一样，版本控制给知识库提供了"敢改"的底气。
{: .prompt-tip }

## 二、Obsidian Git：自动化的日常操作

Obsidian Git 插件把 Git 集成进编辑器：

- **定时自动提交**：如每 30 分钟自动 commit + push，无需手动干预。
- **启动时自动拉取**：打开即与远程同步。
- **手动触发提交**（Ctrl+P → 命令面板）：写描述性提交信息，标记重要版本节点。
- **查看历史**：可视化所有提交与文件变更。
- **分支策略**：大型实验性改动建分支，不影响主分支。

### 推荐的提交习惯

```bash
# 典型流程
git add -A
git commit -m "docs: 新增 XX 主题笔记与参考资料"
git push -u origin main
```

提交信息建议用类型前缀（`docs:` 文档、`feat:` 新功能笔记、`fix:` 纠错），让历史一目了然。

> 自动提交虽省心，但**重要节点仍建议手动提交并写清描述**，否则历史里全是无意义的"Update"。
{: .prompt-info }

## 三、安全实践要点

1. **仓库必须私有**：笔记可能包含工作与个人敏感内容，绝不能推到公开仓库。
2. **密钥不落笔记**：任何 API Key、密码一律不写进笔记文件——本文即遵循该原则。
3. **.gitignore 排除垃圾**：排除缓存、插件数据、临时文件，保持历史干净。
4. **敏感目录不上云**：若用云同步工具，敏感目录应排除或加密。

```gitignore
# 常见忽略项
.trash/
.obsidian/workspace.json
.smart-env/
*.tmp
```

> 最大的事故往往是"手滑推到公开仓库"。**发布前先确认仓库可见性**，比任何技术手段都重要。
{: .prompt-warning }

## 四、进阶用法

- **双设备协作**：一台编辑、一台审阅，靠 pull/push 同步。
- **定期打标签**：如每年年末 `git tag v2026-year-end`，便于回溯。
- **与自动化结合**：结合脚本实现"每日自动摘要提交"（把当天笔记整理成一条提交信息）。

## 小结

给笔记库装上 Git，等于给它装了"后悔药"和"异地备份"。Obsidian Git 插件让这一切足够自动：定时提交、启动同步、误删回退、多端一致。守住三条底线——**仓库私有、密钥不落笔记、敏感目录不上云**——就能放心积累。
