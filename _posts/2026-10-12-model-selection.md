给 AI 工作流接大模型时，一个常见问题是"到底该用哪个模型"。答案不在参数表里，而在**你的任务类型**里。本文给出一套可复用的选型方法。

> 本文价格为**记录当时**的行情，仅用于说明选型思路；实际接入请以模型官网最新公示为准。API Key 等凭据请妥善保管，不要写入任何公开文档或代码仓库。
{: .prompt-warning }

## 一、按任务匹配模型，而不是按名气

大多数接入大模型的工作流，任务可归为三类：

| 任务类型 | 特征 | 选型倾向 |
|---|---|---|
| 日常问答 / 总结 / 翻译 / 搜索 | 输出短、调用频繁 | 轻量快速模型（Flash 级） |
| 复杂推理 / 长文档分析 / 代码生成 | 输出长、逻辑重 | 强力模型（Pro 级） |
| 单篇敏感文档处理 | 数据敏感 | 配合"仅当前文档"模式，规避云端检索 |

> 一个实用原则：**把强模型当"专家"，把快模型当"日常"**。默认走快模型，遇到硬骨头再切强模型，成本与体验两头兼顾。
{: .prompt-tip }

## 二、上下文窗口：能一次看多少

上下文窗口决定模型一次能"读"多少内容。以百万级 token 为例：

- 相当于一次性处理几十页文档；
- 与一篇很长的文档对话时，模型也能看到全文而不必切碎。

> 上下文越长越好吗？不一定。长上下文的成本随 token 数上升，且无关信息会稀释注意力。**能用摘要就不用全文**。
{: .prompt-info }

## 三、Token 成本怎么算

模型通常按"输入 / 输出"分别计费（元 / 百万 token）：

- **输入**：你发给模型的提示词、检索到的文档片段。
- **输出**：模型生成的回复。

**省成本的三个动作**：
1. 减少无关检索片段（精准检索优于全量塞入）。
2. 日常任务用快模型，输出自然更短更便宜。
3. 对话历史定期"压缩"，丢弃冗长往返。

> 以"输出通常比输入贵"为直觉，限制回答长度（如"三句话内"）往往是最有效的省钱手段。
{: .prompt-tip }

## 四、一份选型清单

接入前问自己四个问题：

1. **任务类型**？日常/攻坚，决定快模型还是强力模型。
2. **上下文需求**？单篇对话还是跨文档综合，决定窗口要求。
3. **调用频次**？高频场景成本敏感，考虑快模型。
4. **数据敏感度**？涉及敏感内容，配合仅处理当前文档的模式。

## 小结

模型选型不是技术难题，而是**需求匹配**问题：按任务类型分档、按上下文定窗口、按频次控成本、按敏感度划边界。把"默认快模型 + 攻坚切强模型 + 单篇模式护隐私"作为默认策略，就能以最小成本获得稳定体验。
